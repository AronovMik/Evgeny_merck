# `main` как курируемая библиотека (а не trunk)

**Дата:** 2026-05-18
**Статус:** принято **временно** (ревизия — 2026-07-01)

## Контекст
Claude Code на web создаёт для каждой сессии собственную feature-ветку вида `claude/<task>-<id>`. К текущему моменту в репозитории три параллельных ветки от общего предка `ba429d6`: эта (`claude/setup-concor-repo-y5YDu`), «Школа ИБС» (`claude/school-ibs-session-9hJ00`) и «Клинические случаи Конкора» (`claude/concor-clinical-cases-AVQ5a`). Без явной модели «что есть канон»: новые сессии не знают, откуда стартовать; работа разносится по веткам и не пересекается; default branch неправильно стоит на feature-ветке настройки.

## Рассмотренные варианты

### Вариант 1. Trunk-based: все сессии мёрджатся в `main` по завершении задачи
**Плюсы.** Единственный источник правды. Знание из одной сессии доступно остальным. Нет курационного налога — стандартный git-flow. Так работают все профессиональные команды эмпирически, потому что меньше теряется работы.

**Минусы.** `main` накапливает всё, включая разовые задачи (письма под событие, заброшенные эксперименты). Конфликты на `STATE.md` / `TODO.md` / `CLAUDE.md` при параллельных сессиях. Нужна дисциплина «не пускать слабую работу в merge», иначе main быстро становится свалкой.

### Вариант 2. `main` как курируемая библиотека, feature-ветки изолированы (принято)
**Плюсы.** Библиотека остаётся чистой по построению. Сессии-эксперименты не загрязняют канон — провалившаяся ветка просто остаётся тупиковой. Естественно для **единственного пользователя**, который сам курирует контент. Легче эволюционировать в сторону trunk-based, чем наоборот.

**Минусы.** Курационный налог: каждое «перенеси X в main» — интервент в рабочий поток. Знание может застрять в feature-ветках, если забыть перенести. Состояния `STATE.md` расходятся между ветками — истина склеивается у пользователя в голове.

## Принятое решение
**Вариант 2, временно.** `main` — курируемая библиотека общих ресурсов. Feature-ветки сессий **не сливаются автоматически** в `main`. Перенос — только по явному запросу пользователя, с прицельной cherry-pick / `git checkout origin/<branch> -- <path>`.

Правила реализации — в `CLAUDE.md`, раздел «Архитектура веток».

## Критерии пересмотра (2026-07-01)

Переходим на **вариант 1 (trunk-based с обязательным merge при завершении задачи)**, если за период наблюдения зафиксировано **любое** из:

1. **3+ раза** пришлось просить «перенеси из ветки X в main» — курационный налог высок и сам по себе указывает, что наследие не остаётся в feature-ветках, а должно жить в `main`.
2. **Хотя бы раз** две параллельные сессии независимо решили одну и ту же задачу или собрали один и тот же материал — потеря координации, которую trunk-based бы предотвратил.
3. **Хотя бы раз** ценная работа в feature-ветке оказалась забыта/не перенесена и обнаружена постфактум.

Если ни один критерий не сработал — оставляем текущую модель и продлеваем ревизию ещё на 6 недель.

## Последствия

- Шаг для пользователя (вне Claude): переключить default branch на `main` в GitHub Settings → Branches. До этого момента default остаётся на `claude/setup-concor-repo-y5YDu`, а `main` — копия с правильным именем, готовая принять статус default.
- После переключения default — старая ветка `claude/setup-concor-repo-y5YDu` удаляется в следующей сессии (одной командой `git push origin --delete claude/setup-concor-repo-y5YDu`).
- Эта (библиотечная) сессия продолжает работать на `claude/setup-concor-repo-y5YDu` до конца своего жизненного цикла, при каждом пуше дублируя коммиты в `main` (`git push origin claude/setup-concor-repo-y5YDu:main`).
- Будущие библиотечные сессии (после переключения default) будут работать **прямо на `main`** или на короткой feature-ветке с быстрым fast-forward.

## Альтернатива, если модель не сработает

Переход на вариант 1 потребует:
1. Обновить раздел «Архитектура веток» в `CLAUDE.md`: убрать «не мёрджить автоматически», добавить «в конце сессии — открывать PR в `main`».
2. Один раз провести инвентаризацию всех висящих feature-веток и слить их в `main` (с разрешением конфликтов).
3. Создать в `CLAUDE.md` чеклист «что считать готовой работой, достойной merge» — чтобы решить проблему «main как свалка» дисциплиной, а не архитектурой.
