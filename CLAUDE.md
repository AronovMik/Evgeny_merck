Этот файл автоматически загружается Claude Code как контекст проекта.

Полный свод правил поведения, верификации источников, комплаенс-ограничений и приоритизации — в @INSTRUCTIONS.md. Применять во всех задачах без исключения.

## Контекст проекта

Репозиторий федерального медицинского советника Merck Russia (кардиология). Используется для подготовки материалов по портфелю β-блокаторов (Конкор, Конкор АМ, Конкор НСТ) и для других медицинских/научных задач.

**Портфель Конкор® (β-блокаторы на основе бисопролола):**
- **Конкор** — бисопролол моно, 5 / 10 мг. Показания: АГ, стабильная стенокардия, ХСН.
- **Конкор АМ** — фиксированная комбинация бисопролол + амлодипин (5+5, 5+10, 10+5, 10+10 мг). Показание: АГ.
- **Конкор Кор** — бисопролол моно, 2,5 мг (отдельная регистрация специально для титрации в ХСН). Показание: **только ХСН**.
- **Конкор НСТ** — фиксированная комбинация бисопролол + гидрохлортиазид 6,25 мг (3 дозировки: 2,5+6,25, 5+6,25, 10+6,25). Показание: АГ.

Регистрационные документы (ОХЛП) — в `context/product-info/`, по подпапке на препарат. Сводный перечень — `context/product-info/INDEX.md`. При работе с показаниями, дозами, противопоказаниями — источник истины **только** оттуда, не из памяти модели.

Инструкции написаны под более широкий портфель (включают упоминания SGLT2-ингибиторов / канаглифлозина) — это не ошибка, они универсальны для всех задач Евгения, не только Конкор.

## Архитектура веток (ОБЯЗАТЕЛЬНО)

Репозиторий устроен как **«`main` = курируемая библиотека + независимые feature-ветки сессий»**. Это **не trunk-based**: ветки сессий **не сливаются автоматически** в `main`. Полное обоснование, рассмотренные альтернативы и критерии пересмотра модели — в `decisions/2026-05-18_main-as-library-model.md` (модель временная, ревизия — 2026-07-01).

### `main` — общая библиотека

В `main` лежит то, что должно быть доступно из любой сессии Claude Code:
- Правила: `CLAUDE.md`, `INSTRUCTIONS.md`, `README.md`.
- Справочный контекст: всё содержимое `context/` (guidelines, key-studies, product-info, portfolio, slide-library).
- Зафиксированные решения: `decisions/`.
- Шаблоны: `templates/`.
- Архив исторических чатов: `archive/claude-chats/`.
- Зрелые идеи: отдельные файлы в `ideas/` (не сырой `INBOX.md`).
- Контрольные файлы: `STATE.md`, `TODO.md` — в «библиотечном» смысле (фокус всего проекта в целом).

В `main` **не попадает автоматически**:
- Конкретные задачи из `tasks/` других сессий (KOL-ответы под событие, разовые слайдсеты, аналитические справки) — это конечный продукт сессии, живёт на её feature-ветке.
- Журнальные записи (`journal/`) других сессий — локальный лог конкретной работы.
- Обновления `STATE.md` / `TODO.md` / `CLAUDE.md` из других сессий — **не автомёрджатся**.

### Правила для **библиотечной** сессии (этой)

- Эта сессия — «менеджер библиотеки». Только из неё ведётся запись в `main` напрямую.
- Содержательные изменения уровня библиотеки (правила, контекст, decisions, slide-library и т. п.) — коммитим, пушим, **дублируем в `main`** через `git push origin <branch>:main` или fast-forward.
- Если в библиотечной сессии возникает разовая узкая задача (черновик письма, слайд под конкретное событие) — её лучше уводить в новую feature-сессию. Либо явно складывать в `tasks/` с пониманием, что это разовый артефакт, а не библиотечный ресурс.

### Правила для **других** сессий (любая сессия, не являющаяся библиотечной)

- **Старт сессии:** прочитать `STATE.md`, последнюю запись `journal/`, `TODO.md`, `archive/claude-chats/PREVIOUS_CHATS.md`, `context/slide-library/INDEX.md` из своей ветки (которая создана от `main`, то есть содержит свежую библиотеку). При необходимости подтянуть свежие библиотечные файлы: `git fetch origin main && git checkout origin/main -- <путь>`.
- **Во время работы:** коммитить **только** в свою feature-ветку (`claude/<имя-сессии>-<id>`). **Никаких прямых коммитов в `main`.**
- **Конец сессии:** **НЕ мёрджить в `main` автоматически.** Работа остаётся на feature-ветке. Это сохранит библиотеку чистой; перенос — только по явному запросу пользователя.
- **Если пользователь явно говорит «положи это в библиотеку» / «перенеси в main»:** предложить два пути — (а) открыть библиотечную сессию и попросить курируемый перенос там, либо (б) запросить разрешение и сделать прицельный коммит/cherry-pick в `main` прямо здесь. В commit message обязательно зафиксировать происхождение: `Lift <file> from claude/<source-branch>`.

### Перенос файлов между ветками — практические команды

- Точечно: `git checkout origin/<branch> -- <path>` (берёт только указанный путь).
- Целым коммитом: `git cherry-pick <sha>`.
- Просмотр содержимого файла с другой ветки без изменения текущего состояния: `git show origin/<branch>:<path>`.
- При переносе в `main` — всегда указывать в сообщении коммита источник и причину.

## Workflow сессии (ОБЯЗАТЕЛЬНО)

**В начале каждой сессии:**
1. Прочитать `STATE.md` — понять, где остановились.
2. Прочитать последнюю запись в `journal/` — увидеть детали предыдущей сессии.
3. Заглянуть в `TODO.md` (раздел Active).
4. Просмотреть `archive/claude-chats/PREVIOUS_CHATS.md` — знать, какие исторические чаты доступны. **Сами файлы чатов читать только по явной команде Евгения** («подтяни чат про…», «загрузи архив по…»). Не подгружать содержимое автоматически.
5. Только после этого приступать к запросу пользователя.

**В конце каждой непустой сессии (перед коммитом):**
1. Обновить `STATE.md`: фокус, последние решения, точка возврата.
2. Добавить запись в `journal/YYYY-MM-DD_короткое-описание.md` по шаблону (см. `journal/README.md`).
3. Обновить `TODO.md`, если появились/закрылись задачи.
4. При принятии крупного стабильного решения — создать файл в `decisions/YYYY-MM-DD_тема.md`.
5. **При переносе нового чата из claude.ai** — добавить запись в `archive/claude-chats/PREVIOUS_CHATS.md` по шаблону (одна запись на чат).
6. Закоммитить с описательным сообщением.

### Когда коммитить и пушить (приоритет — сохранность в GitHub)

Главная цель: если что-то случится с локальной сессией Claude или с аккаунтом Claude в принципе, всё содержательное должно уже быть в репозитории на GitHub.

- **Содержательные изменения пушить как можно скорее, не дожидаясь конца сессии.** К содержательным относятся: новые/изменённые файлы в `tasks/`, `context/`, `decisions/`, `ideas/` (зрелые идеи), `templates/`, `archive/claude-chats/`; обновления `CLAUDE.md` / `INSTRUCTIONS.md` / `STATE.md` / `TODO.md`; журнальные записи по реальной работе. Правило: завершён логически законченный шаг → сразу `commit` + `push`, потом продолжаем.
- **Чисто разговорные сессии не пушить и не журналировать.** Объяснения «что такое X», вопросы про сам Claude Code / git / устройство среды, общие обсуждения, которые не порождают артефактов в репозитории, — оставлять только в чате. Если за сессию ни один файл репозитория содержательно не изменился, коммита быть не должно, запись в `journal/` тоже не нужна.
- **Сомневаюсь, относится ли изменение к содержательным, — пушить.** Лишний коммит безопаснее потерянной работы.
- **Промежуточные пуши внутри длинной сессии — норма**, а не исключение. Несколько коммитов за сессию лучше, чем один в конце.

## Рабочие принципы для этого репозитория

1. **Каждая задача — отдельный файл** в соответствующей подпапке `tasks/`. Именование: `YYYY-MM-DD_короткое-описание.md`.
2. **Используемые источники** перечислять в конце файла задачи (PMID/DOI), даже если они уже лежат в `context/key-studies/`.
3. **Препарат-специфика**: при подготовке материалов для конкретного препарата явно указывать его в заголовке файла (Конкор / Конкор АМ / Конкор НСТ).
4. **Off-label и непрямые сравнения** маркировать в тексте, а не только в комментарии (см. Блок 5 INSTRUCTIONS.md).
5. **Рамка гайдлайнов**: при рецензировании клинических случаев, материалов и постов всегда явно фиксировать, по каким рекомендациям идёт оценка — КР МЗ РФ, ESC, ESH, AHA/ACC или иные. Если рамка не задана пользователем — уточнить до начала разбора. Расхождения между гайдлайнами (например, КР МЗ РФ vs ESC) — отмечать явно, не выбирая «победителя» без запроса.
6. **Библиотека слайдов (`context/slide-library/`)**: при появлении любой задачи на слайды/презентации — **до начала работы с нуля** открыть `context/slide-library/INDEX.md` и проверить, нет ли релевантной деки или отдельных переиспользуемых слайдов. Если есть — предложить Евгению использовать их как основу. Сами `.pptx` тяжёлые: подгружать содержимое только при явной необходимости, ориентироваться по MD-карточкам.
7. **Методология построения слайдсетов**: при подготовке любого нового слайдсета по умолчанию применять принципы из `decisions/2026-05-18_slide-building-principles.md` (слайд = одно исследование; заголовок-вывод; дисклеймер «получены у» для off-label популяций; нет утверждения превосходства без межгруппового p; слайды-резюме блоков; «меню для эксперта» для крупных деков; и др.). Отклонения — обосновывать явно.
8. **Верификация расчётов и формулировок** (обязательно). Все числовые расчёты — суточный индекс СМАД, формула Фридевальда, ИМТ, СКФ CKD-EPI, процент снижения, SCORE2, BSA, индексы ГЛЖ (Соколов-Лайон, Корнелл), стратификация ССР и т. п. — выполнять с явным выписыванием формулы и подстановки, не «по памяти». **При проверке любого внешнего материала (кейс пользователя, чужой текст), содержащего числовые значения, явно прогонять каждое значение через соответствующую формулу/норму с первой же итерации — НЕ дожидаясь, пока пользователь поймает несогласованность.** Формулировки диагнозов — строго по образцам из соответствующего клинрека КР МЗ РФ в `context/guidelines/` (например, для пациента на АГТ степень АГ не указывается — фиксируется достижение/недостижение целевого АД). Перед тем как утверждать клинический факт (порог, цель, классификацию, противопоказание), сверяться с первоисточником в `context/guidelines/`. Если нужного клинрека или валидированной формулы в репозитории нет — **сообщить пользователю явно** до того, как использовать неверифицированные данные; не реконструировать «по памяти» и не заимствовать молча из ESC/ESH без отметки.
9. **Роль клинического эксперта по умолчанию.** В медицинских/научных задачах Claude действует как эксперт в соответствующей области (кардиолог, фармаколог и т. п.) **автоматически, без отдельного запроса**. Это включает построчную клиническую проверку всех формулировок: метод исследования должен соответствовать получаемой информации (характер ритма — только по ЭКГ, не по пальпации/СМАД; локальная сократимость — только по ЭхоКГ; ишемия миокарда — по нагрузочной пробе или коронароангиографии и т. д.); единицы измерения и пороговые значения — по КР МЗ РФ; терминология — формальная, без бытовых эквивалентов. При запуске LLM Council по медицинскому материалу advisors обязаны проверять весь текст кейса построчно на клиническую достоверность, а не только верхнеуровневую стратегию — в framed question для совета это включать явно.
10. **Запуск LLM Council — стандартный пайплайн для этого репо.** При триггерных фразах («council this», «pressure-test this», «war room this», «stress-test this», «debate this», «run the council», «прогони совет» и т. п.) — следовать методологии из `LLM_COUNCIL.md` со следующими **модификациями стандартного пайплайна Karpathy**:

    (а) **Verification pass — ДО запуска совета.** Сверить кейс построчно с `context/guidelines/` (КР МЗ РФ и иные клинреки) и `context/product-info/` (ОХЛП препаратов портфеля). Все находки (подтверждённые факты, расхождения, отсутствующие первоисточники) включить в framing для advisors как факты, а не как мнения. Если требуемого клинрека или ОХЛП в репозитории нет — сообщить пользователю явно (по принципу №8).

    (б) **Context-enrichment вопрос — обязательный, всегда.** Перед framing chairman **ВСЕГДА** задаёт пользователю один структурированный вопрос со списком (даже если что-то из этого видно из промпта): целевая аудитория (специальность, опыт врачей; формат — медпред-визит / KOL-встреча / самостоятельная презентация эксперта); главная цель (что должен сделать / узнать / запомнить врач после кейса); что продвигаем (продукт / комбинация / концепция; есть ли конкретный USP, который должен быть в центре); особые ограничения (off-label-зоны, locked-решения пользователя, чего избегать). Без явного ответа на эти 4 пункта совет не запускать. Ответ становится частью framing для всех трёх advisor — рамка одинаковая. Исключение — если пользователь явно сказал «без context-вопроса, используй то, что в чате»: тогда chairman сам конструирует рамку из доступного и фиксирует это в framing.

    (в) **3 кастомные роли вместо 5 generic-ролей Karpathy.** Запуск всех трёх в параллель.

    - **Кардиолог 1 (защита, эксперт экстра-класса).** Аргументы за клиническую состоятельность кейса: реалистичность пациента (внутренняя согласованность анамнеза, осмотра, лабы); точность формулировок диагнозов **строго по образцам КР МЗ РФ**; корректность сопутствующей терапии (каждый компонент по своему показанию, без избыточности); клиническая интересность (узнаваемость в реальной российской практике, не учебная стерильность). Опора — клинреки в `context/guidelines/` + ОХЛП в `context/product-info/`.

    - **Кардиолог 2 (оппонент, эксперт экстра-класса).** Поиск нестыковок, методологических дыр, провоцирующих моментов, ошибок в формулировках диагнозов и сопутствующей терапии, «сырых» формулировок, мест, где детализация скатывается в учебный шаблон. Симулирует подготовленного кардиолога-аудитора, который ищет, к чему можно прицепиться. Опора — те же клинреки и ОХЛП.

    - **Маркетолог Merck (guardian позиционирования + off-label-вахта).** Читает те же документы, что и кардиологи (ОХЛП, КР МЗ РФ, `context/slide-library/`), но смотрит сквозь маркетинговую линзу. Главные фильтры **по приоритету**: (1) **Off-label-вахта** — любое утверждение, USP или подразумеваемое позиционирование, выходящее за раздел 4.1 ОХЛП продвигаемого препарата, — красный флаг; off-label требует явного дисклеймера по правилу 4 `decisions/2026-05-18_slide-building-principles.md` либо переписки; (2) **Видимость и уникальность продукта** — USP-блок присутствует, дифференциаторы из ОХЛП озвучены так, что замена продукта на конкурента невозможна без потери смысла; (3) **Тоннель внимания** — каждая клиническая деталь работает на позиционирование, иначе — кандидат на сокращение или вынос в сноску; (4) **Дрейф** — кейс заканчивается продуктовым выводом, а не клиническим. Дополнительная функция — «небрежность-сторож»: «сырые» формулировки, бытовые синонимы, опечатки в шифрах флагить как риск восприятия (не править — это зона кардиологов). Что маркетолог НЕ делает: не предлагает альтернативные стратегии позиционирования, не оценивает тон, не симулирует KOL-feedback, не уходит вглубь клинического содержания глубже, чем нужно для позиционирования. При неуверенности явно квалифицирует утверждение как «суждение guardian без формального источника» vs «compliance-наблюдение по ОХЛП X».

    (г) **Принцип №9 применяется ко всем трём advisor.** Каждый обязан произвести построчную клиническую/маркетинговую проверку всего текста кейса (по своей зоне ответственности), а не только верхнеуровневую стратегию. Это включается в framed question явно.

    (д) **Числовая когерентность нарратива.** Для каждого шага плана лечения каждый advisor обязан проверить: (1) цифры финала шага согласуются с заявленным словесным выводом — если АД выше цели или ФК не достигнут, формулировка «эффективность подтверждена» некорректна; (2) дельта показателей между шагами плаузибельна при заявленных изменениях дозы/препарата — большая дельта без изменения доз требует механистического объяснения и должна укладываться в обычные значения эффекта (например, переход со свободной комбинации на FDC даёт ~5–8 мм рт.ст. за счёт устранения пропусков, не 14); (3) интервалы между шагами реалистичны для конкретной задачи — при стенокардии 7–14 дней достаточно для оценки антиангинального эффекта β-блокатора, для коррекции АД интервалы могут быть длиннее (2–4 нед). Несоответствия флагить явно с указанием строки.
