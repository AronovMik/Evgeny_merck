# 2026-05-18 — Архитектура веток: main как курируемая библиотека

## Контекст
В репозитории к этому моменту три параллельных feature-ветки сессий, все ответвлены от общего предка `ba429d6`: эта (настройка), «Школа ИБС», «Клинические случаи Конкора». Default branch стоял на feature-ветке настройки. Это создавало путаницу: новые сессии стартуют от чего-то полу-случайного, а работа из одной сессии не доходит до других.

Евгений сформулировал предпочтительную модель: `main` — курируемая библиотека общих ресурсов; другие сессии **не пушат в main автоматически**, перенос — только по явному запросу.

Я предложил честный анализ: trunk-based лучше как индустриальный стандарт, но для единственного пользователя на стадии нащупывания workflow курируемая модель уместнее и легче эволюционирует в trunk-based, чем наоборот. Принято: модель курируемой библиотеки, временно, с ревизией 2026-07-01.

3. Хотя бы раз ценная работа в feature-ветке забыта — потеря работы.

## Решения
- **`main` создан от feature-ветки**, а не «пустым с нуля». Логика: эта ветка уже содержит всё библиотечное (правила, контекст, slide-library, гайдлайны, decisions). Стартовать `main` с пустого корня и потом наполнять — лишняя работа без выигрыша.
- **Другие сессии в main не мёрджатся прямо сейчас.** Их работа («Школа ИБС», «Клинические случаи Конкора») остаётся на их ветках до явного запроса.
- **Модель явно помечена как временная** с конкретной датой и критериями пересмотра — чтобы не превратиться в наследие, которое все стесняются трогать.

## Что осталось / следующий шаг

- Эта сессия до конца жизненного цикла продолжает работать на `claude/setup-concor-repo-y5YDu`, при каждом пуше дублируя коммит в `main` (`git push origin claude/setup-concor-repo-y5YDu:main`).
- Будущие библиотечные сессии работают прямо на `main`.
- Если другие сессии попросят «положи в библиотеку» — переносить точечно через `git checkout origin/<branch> -- <path>` с явным указанием происхождения в commit message.
